At 60 Hz a screen shows a new frame every 1000 / 60 = 16.7 ms. That is the rendering budget: the time the browser has to run your code and produce the next frame. web.dev puts your share lower, at about 10 ms, because the browser has its own work in every frame. The cheapest way to stay inside it is to not ask for frames you don't need: the star field behind this site costs about 1 ms per frame while the pointer moves, and nothing once the pointer has been still for about 440 ms.

## Where the 16.7 ms goes

The number is arithmetic. `requestAnimationFrame` callbacks generally run at the display's refresh rate, and [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame) names 60 Hz as the most common, with 75, 120 and 144 Hz also widely used. At 120 Hz the budget is 8.3 ms. At 144 Hz it is 6.9 ms.

Inside that window the browser walks what web.dev calls the [pixel pipeline](https://web.dev/articles/rendering-performance): JavaScript or CSS changes something, then style, layout, paint and composite. Not every change pays for every step:

- Changing geometry, like `width` or `top`, makes the browser lay the page out again, repaint what moved and composite the result.
- A paint-only property, like `color` or `box-shadow`, skips layout.
- A change that needs neither layout nor paint goes straight to compositing. web.dev calls it the cheapest path, and the one to use for animations and scrolling.

The same article says that when your work doesn't fit the budget, the frame rate drops and the page judders. So the budget has two sides: what one frame costs, and how many frames you ask for.

## Long tasks spend several frames at once

The main thread runs one task at a time. web.dev [defines a long task](https://web.dev/articles/optimize-long-tasks) as any task over 50 ms, and [MDN](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongTaskTiming) lists what long tasks cause: delayed input, slow event handling, janky animations and scrolling. 50 ms is three whole frames at 60 Hz. While a task runs, the browser can't respond to input.

web.dev's advice is to break long tasks into smaller ones and yield to the main thread between them, with `scheduler.yield()` where it exists, so input can be handled in the gaps. The other half is choosing when heavy work runs. Downloading a script queues tasks to parse and compile it, and the biggest script on this site is the three.js chunk (three 0.182 with React Three Fiber 9) behind the planet. It is loaded lazily, and only after three things have happened:

```tsx title="src/components/three/SkyCanvas.tsx"
const idle = () =>
  new Promise<void>((r) => ('requestIdleCallback' in window ? requestIdleCallback(() => r(), { timeout: 4000 }) : setTimeout(r, 1500)));
// …
      if (weakDevice()) return setMode('static');
      await loaded();
      await document.fonts.ready;
      await idle();
```

The page's `load` event, then the fonts, then an idle callback. The planet appears a moment later than it could. The comment at the top of the file gives the trade: the chunk "never competes with the LCP font".

## A loop that runs only while something moves

The dots behind this site are drawn by `src/scripts/field.ts` on a 2D canvas. On every page except articles like this one, a mouse pointer acts as a gravitational lens: dots near the cursor are pushed outward into a ring, and faint dust that is invisible at rest shows up in the ring. At 1440×900 that is 3,750 points: 1,500 visible stars, plus 2,250 dust points drawn only while a lens is active. The canvas is 2880×1800 device pixels at a device pixel ratio of 2 (the cap).

Nothing runs until the pointer moves:

```ts title="src/scripts/field.ts"
function wake() {
  if ((live || hTarget || hs || dawn0) && !raf && !document.hidden) raf = requestAnimationFrame(frame);
}
// …
window.addEventListener(
  'pointermove',
  (e) => {
    if (!live || e.pointerType === 'touch') return;
    tx = e.clientX;
    ty = e.clientY;
    // …
    target = 1;
    wake();
  },
  { passive: true },
);
```

The event handler does almost nothing. It records where the pointer is and asks for a frame, but only if none is pending, so several `pointermove` events between two frames still cost one frame. The frame does the work and decides whether it needs another:

```ts title="src/scripts/field.ts"
function frame(now: number) {
  raf = 0;
  const dt = last ? Math.min(now - last, 64) : 16;
  last = now;
  const k = 1 - Math.exp(-dt / FOLLOW);
  lx += (tx - lx) * k;
  ly += (ty - ly) * k;
  s += (target - s) * (1 - Math.exp(-dt / FADE));
  let busy = false;
  if (Math.abs(tx - lx) < 0.1 && Math.abs(ty - ly) < 0.1) {
    lx = tx;
    ly = ty;
  } else busy = true;
  if (Math.abs(target - s) < 0.004) s = target;
  else busy = true;
  // …
  draw();
  if (busy) raf = requestAnimationFrame(frame);
  else last = 0;
}
```

Three details keep it inside the budget:

- `requestAnimationFrame` is one-shot. MDN says the callback has to call it again to get another frame, so stopping is just not asking. Once the lens is within 0.1 px of the pointer and its strength has settled, `busy` stays false and the loop ends. The parts cut from the excerpt (the black hole's lens, shockwaves, the big bang's dawn) set `busy` the same way.
- The ease uses the frame's timestamp. The lens chases the pointer with a 70 ms time constant (`FOLLOW`), computed from `dt`, so it moves at the same speed at 60 Hz and at 120 Hz. MDN warns that animations which ignore the timestamp run faster on high refresh-rate screens. `dt` is clamped to 64 ms, so after a stall the lens covers at most about 60% of the remaining distance in one frame instead of jumping.
- Nothing is allocated per frame. Positions live in typed arrays sized on resize, and `draw()` fills squares grouped by colour, so `fillStyle` is set at most once for each of its 24 colour buckets.

When the tab is hidden, most browsers already pause `requestAnimationFrame`. The file cancels its frame anyway and resets `last`, so the first frame back uses a 16 ms step instead of the whole time away. On article pages, without a fine pointer, or under reduced motion, the lens never starts: the field is drawn once and stays still, apart from the big bang.

## What it costs, measured

I measured the loop in Chrome 154 on an Apple M5 Mac: the production build served locally, 1440×900 at a device pixel ratio of 2, no CPU throttling, and the 3D planet kept off so only the dust was drawing. A wrapper around `requestAnimationFrame` timed every `frame()` call. A script dispatched a synthetic mouse `pointermove` every 8 ms for 5 seconds, then kept still for 3 seconds. Three runs:

| Run | Callbacks | Mean | p95 | Max | Last frame after the last move |
|---|---:|---:|---:|---:|---:|
| 1 | 326 | 0.96 ms | 1.1 ms | 3.5 ms | 430 ms |
| 2 | 327 | 0.90 ms | 1.1 ms | 1.3 ms | 443 ms |
| 3 | 326 | 0.68 ms | 1.1 ms | 1.2 ms | 443 ms |

While the pointer moved, frames arrived every 16.7 ms (median) and none were dropped. A frame cost 0.68 to 0.96 ms on average: under 6% of a 16.7 ms frame, and under a tenth of web.dev's 10 ms.

Then the loop stopped. The last frame ran 430 to 443 ms after the last pointer move, and there were no callbacks at all for the remaining ~2.55 s of each run. With the pointer still in the window and nothing else moving, the only thing keeping the loop busy is the lens closing its last gap to 0.1 px. 430 to 443 ms is a little over six of its 70 ms time constants; how many it takes depends on how far behind the pointer the lens was when the pointer stopped.

Two limits on these numbers. The wrapper times main-thread JavaScript, including the canvas calls, but not rasterising or compositing, and the timer resolution was 0.1 ms. And this is one fast Mac at 60 Hz. I haven't measured the loop on a phone.

## The rule behind it

The site's working rules say it in four words: idle means zero work. In practice that comes down to a few habits:

- Request a frame from the event that changed something, not from a loop that is always running.
- Make every frame prove the next one is needed. Each moving part sets `busy`; if none does, the loop ends.
- Ease with the timestamp, never the frame count.
- Keep big parsing and setup work away from the first frames: after `load`, fonts and an idle callback.
- Measure two things: what a frame costs, and how quiet the page gets once nothing moves.

The planet is the exception on purpose. It animates all the time, so it caps itself instead of stopping: React Three Fiber's `frameloop="demand"`, with the scene rendering about 29 times a second while idle and parking on article pages.
